## Write code using expressive typing (where available)

Expressive typing in signatures of functions, methods, fields etc. provides strong signals about intent to humans as well as AI agents. It can also provide far-reaching consistency guarantees, reduce the amount of tests needing to be written, and reduce the amount of code itself through powerful abstractions and generalizations. This requires care and a measured approach to not abstract prematurely, abstract to the point of losing focus and forcing disjoint things together or introduce too much indirection / complexity. Expressive typing ranges from basic types, function-types, to generics (type-variables, parametric polymorphism), bounded / constrained parametric polymorphism via subtyping and/or typeclasses, type-level composition via traits / mixins, unions, intersections, algebraic data types (ADT / ADTs: products, co-products etc.), GADTs, F-Bounded Polymorphism to refinement types, type members, linear or affine typing features, dependent types / path-dependent types and session types - as well as combinations of all the former. The exact features to use depend on the language, the project conventions and the problem-space. Within each such setting, it is encouraged to encode important domain- and application-invariants whose violation at the type level.

Some specific guidelines for expressive typing are:

* Avoid explicitly using top types (e.g. `any`) unless strictly necessary. Be specific where possible.
* When defining own type-names, chose intelligible, role-functional naming that avoids leaking implementation details and instead tells a clear, high-level conceptual story and hints at known patterns.
* As with values - prefer composition over inheritance, meaning that traits / mixins, typeclasses, interfaces and similar are often better than deep subtyping hierarchies. Most of the use-cases for inheritance can be solved in a more principled and ergonomic manner by using sum and product types (as variants, traits, union-types, records, tuples, classes, structs depending on language) in composition.
* Avoid leaving parameters or return values of functions or methods untyped or implicitly typed. Be explicit and specific.
* In langauges which permit parametric polymorphism (generics), write generic code in every case where the value of unification and abstraction outweighs the cost of complexity and indirection.
* When bounding type-variables (generics), practice interface-segregation. This means charting usage scenarios to define a minimal set of consumer-based contracts (e.g. interfaces, typeclasses) that is sufficient to cover all use-cases while maintaining the principle of least power.
* Avoid both too wide and too narrow typing. Too wide typing (e.g. using top types, or very wide interfaces) can lead to loss of important signals about intent and can allow for invalid states and values to be represented, while too narrow typing can lead to excessive boilerplate, code bloat, and reduced extensibility, composability and reuse. Narrower is often better - but finding the right balance is key.
